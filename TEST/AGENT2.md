**现在的核心任务只有一个：在没有截图输入的情况下，把整个推理链路彻底跑通，验证“认知助手”的核心价值。**

我建议你立刻开始以下 **4 个实战步骤**（这将让你的项目从“写好了组件”变成“真正能用”）：

### 1. 立即进行端到端（E2E）手动集成测试（今天最重要的事）
既然没有 OCR，你可以手动构造 `PlayerView` 的 JSON 数据（也就是 Rust 接收的输入格式）。利用 `serde` 序列化特性，造一个经典的“二选一”或“必雷”残局数据。

- **动作**：编写一个 `input.json`，放入 `src/test_data/`。
- **目标**：启动 `axum` Web 服务，用 `curl` 或前端界面发送这个 JSON，验证整条链路：**JSON -> Rust 推理(Phase 2+3) -> 生成 IR -> 调用 LLM API(Phase 4) -> 返回人话**。
- **验证点**：LLM 是否真的没有编造坐标？IR 里的依赖链条是否被正确翻译成了“因为...所以...”的逻辑？

### 2. 深度打磨 LLM 的提示词（Prompt Engineering）
代码写完只是第一步，LLM 在这个架构里最容易“说胡话”。由于 Phase 4 已经完成，现在是你调优 `System Prompt` 和 `User Prompt` 的最佳时机。

- **动作**：针对几种典型的 IR 数据（高概率雷、低概率安全、多区域策略），反复运行 LLM 翻译。
- **目标**：把“硬编码式话术”彻底剔除。比如要求 LLM 必须使用“**坐标（行,列）** + **具体数字约束**”的句式，禁止模糊表达（如“中间某个格子”）。
- **验证点**：如果 LLM 输出中出现 IR 里不存在的坐标，你现在的代码能否检测并拒绝输出？

### 3. 搭建“手动棋盘编辑器”前端（替代 OCR 暂缺的空窗）
既然 OCR 暂时缺失，你可以把前端页面（Phase 5）改造为一个**手动点击棋盘**。

- **动作**：在前端 HTML/JS 里绘制网格，让用户**左键点出数字**，**右键点出旗帜**，通过界面直接生成 `PlayerView` 发给后端。
- **收益**：这样你就能自己当“OCR”，手动录入任意复杂的扫雷局面。这个工具本身就能用来复盘和教学，比依赖截图更稳定。

### 4. 性能压测与代码洁癖（Polish）
你现在拥有了一个完整的 Rust 后端，可以趁机看看它的极限。

- **动作**：用 `cargo bench`（或简单的循环计时）跑一下蒙特卡洛模拟（Phase 3）。比如在 30x30 的大棋盘、剩余 100 颗雷时，模拟 10000 次需要几毫秒？
- **目标**：如果时间过长，调低蒙特卡洛迭代次数，或用 Rayon 库做并行计算（`par_iter`）。确保 Web 请求在 200ms 内返回，不卡顿。
